FABTRACE DECISION LOG
=====================

Purpose
-------
This is the append-only record of material FabTrace decisions. It was created
on 2026-10-04 and includes a best-effort reconstruction of decisions made before
the log existed.

Future entries must include a stable ID, date, status, decision, rationale, and
consequences. Do not delete or rewrite an old decision when direction changes.
Append a new entry with status SUPERSEDED and reference the earlier decision.
Unresolved proposals belong in the PENDING section and are not authorization to
implement them.


DECISIONS
---------

[D-001]
Date: 2026-10-04
Status: APPROVED
Decision: The project is named FabTrace.
Rationale: The name connects semiconductor fabrication with end-to-end tracing
of orders, events, transformations, and forecasts.
Consequences: The repository, Python package, CLI, and project-local skills use
the FabTrace/fabtrace name.

[D-002]
Date: 2026-10-04
Status: APPROVED
Decision: FabTrace will be an event-driven semiconductor supply-chain digital
twin and control tower for learning data engineering.
Rationale: The project should cover realistic ingestion, ETL, event processing,
data quality, analytical modeling, forecasting, and observability through one
coherent supply-chain problem.
Consequences: Users will eventually configure product dependencies and provider
candidates, place orders, receive provider updates, and inspect progress, cost,
quality, risk, and delivery forecasts.

[D-003]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: FabTrace is developed in its own repository directory alongside the
upstream eto-chip-explorer repository.
Rationale: Application work must remain separate from the imported reference
project.
Consequences: Upstream code is not modified by FabTrace implementation work.

[D-004]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: Copy the five relational ETO CSVs into the capitalized Data directory:
stages.csv, inputs.csv, sequence.csv, providers.csv, and provision.csv. Exclude
website image artifacts and documentation files from application source data.
Rationale: These five tables contain the reference entities and relationships
needed for planning and provider work.
Consequences: Data/ is the immutable source snapshot. The copies were verified
byte-for-byte against the ETO originals using SHA-256 checksums.

[D-005]
Date: 2026-10-04
Status: APPROVED
Decision: Preserve a strict boundary between ETO-sourced facts and synthetic
operational facts.
Rationale: ETO contains identities, capabilities, relationships, geography, and
market information, but not operational order history, capacity, lead time,
price, inventory, quality, or reliability.
Consequences: Synthetic fields must be labeled and reproducible. Market share
must not be treated as evidence of price, reliability, quality, or risk. Source
CSV files must not be edited to fit simulation requirements.

[D-006]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: Use AGENTS.md as the repository-wide agent contract and project-local
.codex/skills/*/SKILL.md files for component-specific workflows.
Rationale: Repository-wide invariants belong in one governing file, while narrow
skills keep task routing and context focused.
Consequences: Seven skills exist for source data, provider simulation, order
planning, event pipelines, update extraction, supply analytics, and the control
tower. Component skills defer to AGENTS.md.

[D-007]
Date: 2026-10-04
Status: APPROVED
Decision: Material technical and domain decisions require explicit user
confirmation before implementation.
Rationale: The user wants architecture choices to remain visible and reviewable.
Consequences: Agents must distinguish proposals from approvals. Routine
mechanical work within an approved decision does not require repeated approval,
but deviations do.

[D-008]
Date: 2026-10-04
Status: APPROVED
Decision: Build and validate the source-data foundation before implementing the
provider simulator.
Rationale: Provider agents need a trustworthy provider and capability catalog.
Consequences: The first implementation milestone is a read-only ETO loader and
validator. Provider execution behavior remains out of scope until its contracts
are approved.

[D-009]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: Use Python 3.12 or newer, uv, Pydantic 2, pytest, a src/ package layout,
and Python's standard CSV parser for the source-data milestone.
Rationale: This is a small, typed, testable foundation without adding a
dataframe or storage dependency before it is needed.
Consequences: pyproject.toml declares Python >=3.12 and the approved dependencies;
uv.lock provides reproducible resolution. The current development interpreter is
Python 3.14.7, which satisfies the declared constraint.

[D-010]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: The source-data layer loads immutable CSVs into validated in-memory
models rather than selecting a database or derived storage format at this stage.
Rationale: Cross-table semantics and data quality should be proven before a
persistence architecture is chosen.
Consequences: Provider aliases are aggregated under provider_id without losing
source-row counts; provision targets may reference input or stage IDs; blank
shares remain unknown; all cross-table references are validated.

[D-011]
Date: 2026-10-04
Status: IMPLEMENTED
Decision: Expose source validation as
"fabtrace data validate --data-dir Data" and fail with a nonzero exit code for
missing files, malformed rows, or invalid references.
Rationale: A CLI makes the source contract observable and reusable in local
development and future automation.
Consequences: The current snapshot validates with 3 stages, 126 inputs, 396
logical provider IDs from 403 rows, 1,300 provision relationships, 139 sequence
relationships, and zero validation errors. Five automated tests pass.

[D-012]
Date: 2026-10-04
Status: APPROVED
Decision: Maintain this log.txt as the append-only record of all material
project decisions.
Rationale: Future agents and contributors need durable context and protection
against silent architectural drift.
Consequences: AGENTS.md requires decision-log updates in the same change as an
approved decision. Corrections and changes must be appended and linked rather
than erasing history.

[D-013]
Date: 2026-10-04
Status: APPROVED

Decision: The first simulation uses organization provider P208 (Shin-Etsu) and

[D-014]
Date: 2026-10-04
Status: APPROVED
Resolves: P-001 and part of P-003
Decision: Use SimPy with a virtual clock where one unit is one simulated day,
a fixed seed of 42, and synthetic start time 2026-01-05T00:00:00Z. The first
lifecycle is CREATED, ACKNOWLEDGED, QUEUED, IN_PRODUCTION, QUALITY_CHECK,
READY_TO_SHIP, SHIPPED, DELIVERED.
Rationale: Virtual deterministic execution makes scenarios fast, reproducible,
and testable.
Consequences: The first happy path uses zero-day acknowledgement, one queue day,
four production days at 25 wafers per day, one quality-check day, and two transit
days. It includes milestone messages and daily production-progress updates.

[D-015]
Date: 2026-10-04

[D-019]
Date: 2026-10-04
Status: APPROVED
Decision: Add a deterministic equipment-failure scenario for PO-0001. After one
production day and 25 completed wafers, incident INC-0001 pauses production for
two simulated days because of equipment_calibration, then production resumes.
Extend the lifecycle with IN_PRODUCTION to BLOCKED to IN_PRODUCTION and add
equipment_failure and production_resumed events.
Rationale: The first exceptional scenario should demonstrate a causal incident,
state interruption, delivery-forecast revision, and unstructured provider update
without introducing random behavior or additional providers.
Consequences: The original delivery forecast of 2026-01-13 changes to 2026-01-15
at the failure event. Incident events carry the incident ID/type/reason, two-day
delay, previous forecast, and current forecast. Subsequent events retain the
revised forecast. The happy-path scenario remains behaviorally unchanged.

[D-020]
Date: 2026-10-04
Status: APPROVED
Decision: Add seeded stochastic equipment-failure generation as a third scenario
mode while retaining no-incident and explicit-incident modes. The synthetic P208
profile uses a 0.5 daily failure probability, at most one failure per order,
weighted downtime of one/two/three days at 0.25/0.5/0.25, and weighted reasons
equipment_calibration/unplanned_maintenance at 0.6/0.4.
Rationale: Seeded stochastic behavior teaches probability distributions and
Monte Carlo-ready simulation mechanics while remaining reproducible and
auditable.
Consequences: Each order's random stream is derived with SHA-256 from scenario
seed and stable scenario/provider/order identities, insulating it from iteration
order. Private truth events retain draw, threshold, distribution result, source,
and stream version; provider messages do not expose random internals. Seed 42
produces a day-3 failure with three downtime days and delivery on 2026-01-16.
Seed 46 produces no failure for the four-day production run. These probabilities
are teaching assumptions, not claims about the source organization.

[D-021]
Date: 2026-10-04
Status: APPROVED
Decision: Add a local raw provider-update ingestion stage exposed as
"fabtrace ingest provider-updates". Ingest provider_updates.jsonl in bounded
batches into generated, gitignored .fabtrace/state/fabtrace.db using Python's
standard-library SQLite. Preserve each original payload unchanged, retain
ingestion/source metadata, enforce idempotency by message_id, and store invalid
or identity-conflicting payloads in a separate append-only quarantine table.
Rationale: This introduces durable raw retention, SQL, replay, validation, and
delivery semantics with the smallest infrastructure suitable for the current
single-process learning milestone.
Consequences: Delivery is honestly described as at-least-once with idempotent
accepted-message writes. Replaying an input does not duplicate accepted rows.
Malformed and unsupported-schema inputs remain inspectable with failure reasons.
The ingestion consumer validates only provider messages and never reads private
simulation ground truth. Kafka/Redpanda, PostgreSQL, extraction, normalized
facts, orchestration, and analytical models remain deferred.

[D-022]
Date: 2026-10-07
Status: APPROVED
Decision: Add Stage 5 provider-update extraction using a deterministic,
standard-library rules-v1 baseline with no new dependency. The extractor reads
only accepted raw provider-message subject/body content and envelope identity
metadata, writes append-only versioned extraction runs, attempts, and typed
claims in the existing SQLite database, and is invoked with a required scenario
boundary through "fabtrace extract provider-updates". Claims cover order status,
progress, completed/ordered quantity, unit, forecast delivery date, delay,
incident reason, and operational milestone date. Each claim retains message and
run provenance, its exact source span, normalized typed value, extractor version,
confidence, and validation status.
Rationale: Exact deterministic rules provide an inspectable, reproducible
baseline against which a later LLM extractor can be measured.
Consequences: Exact supported patterns receive confidence 1.0. Unsupported or
ambiguous text abstains; conflicting order references require review. Replaying
the same message with rules-v1 is idempotent, while a future extractor version
may append independent claims without overwriting history. A separate
"fabtrace evaluate extraction" path may join completed claims to private ground
truth only after extraction and reports field-level exact metrics and
abstentions. LLM/API selection, claim reconciliation into current order state,
human-review workflows, and analytics remain deferred.

[D-023]
Date: 2026-10-07
Status: APPROVED
Decision: Add Stage 6 order-state reconciliation as version order-state-v1,
invoked through "fabtrace reconcile order-state" with a required scenario
boundary. Consume only valid confidence-1.0 rules-v1 claims and write append-only
reconciliation runs, per-message decisions, and order-state snapshots in schema
version 3. Expose the latest snapshot per scenario, order, and reconciliation
version through current_order_state. Process knowledge in received-time order,
retain provider sent time as fact-effective time, carry unchanged fields forward
with field-level source-message provenance, allow approved lifecycle transitions
and repeated production updates, mark wholly older updates stale, and mark
illegal transitions, same-time value disagreements, invalid regressions, or
unresolved extraction as conflicts.
Rationale: Immutable claims need a deterministic temporal projection before
progress, forecast, and risk analytics can consume a coherent order state.
Consequences: Reconciliation replay is idempotent. Current state remains a
source-reported projection rather than a predictive model. It exposes status,
progress, completed/ordered quantity, unit, provider forecast date, reported
delay, incident reason, and latest milestone with as-of/effective times and
provenance. Risk scoring, predictive ETA, cost, quality metrics, human conflict
resolution, and dashboard work remain deferred.

[D-024]
Date: 2026-10-07
Status: APPROVED
Decision: Add Stage 7 operational analytics as operational-metrics-v1, invoked
through "fabtrace analyze orders" with required scenario and timezone-aware
as-of boundaries. Read only order-state-v1 snapshots and reconciliation
decisions observed at or before that as-of time. Write append-only analytics
runs and order metric snapshots in SQLite schema version 4 and expose the latest
as-of result per scenario, order, and metric version through
current_order_metrics. Metrics include current source-reported status/progress,
initial and current provider forecasts, signed forecast drift days, forecast
revision count, signed days to forecast, latest reported delay plus an explicit
presence flag, two-observation progress velocity, latest-update age,
communication lag, and applied/stale/conflict message counts.
Rationale: Dashboard-ready operational signals should be reproducible,
hand-computable, decomposable, and protected from future-data leakage before any
predictive or composite model is introduced.
Consequences: The CLI requires --as-of and analytics replay is idempotent at the
scenario/order/metric-version/as-of grain. Missing reported delay and
insufficient progress history remain NULL rather than becoming invented zeros.
Forecast drift is positive when delivery moves later; age and lag are measured
in fractional days; velocity is percentage points per day. No composite risk
score, predicted ETA, cost, quality, critical path, or dashboard is authorized
by this decision.

[D-027]
Date: 2026-10-11
Status: APPROVED
Decision: Add Stage 10 Planner v1 as planner-v1. Extend material product nodes
with a positive synthetic lead_time_days publication requirement while process
nodes retain positive duration_days. Interpret each dependency-edge quantity as
prerequisite units per unit of its dependent node; recursively expand and sum
shared demand from the customer output quantity. Deterministically select the
first configured provider candidate. Generate one purchase order per material
node and one provider work order per process node; capabilities create checks
but no purchase orders, and the final output creates no provider order. Schedule
nodes with a DAG forward pass from a timezone-aware requested-at instant,
letting independent branches run in parallel and starting each dependent after
all prerequisites finish. Report the longest deterministic branch as the
critical path and the output finish as expected delivery. Provide "fabtrace
plan order" and a local Plan Order page. Write immutable plan.json artifacts
under .fabtrace/plans/<order-id>/ and refuse overwrite. Keep operational SQLite
read-only.
Rationale: A transparent, hand-computable deterministic planner connects
published product recipes to provider orders and expected delivery without
inventing capacity, cost, yield, or uncertainty models that the current data
cannot support.
Consequences: Planning is reproducible from the published product version,
recipe fingerprint, customer quantity, and requested-at time. Material lead
time, process duration, quantities, and provider ordering are explicitly
synthetic configuration. Each graph node remains a separate provider-order
grain. Inventory, consolidation, capacity queues, batching, yield, rework,
cost optimization, and probabilistic dates remain deferred.

[D-029]
Date: 2026-10-11
Status: APPROVED
Decision: Add Stage 11 plan-driven multi-provider simulation through a new
"fabtrace simulate-plan" command. The immutable plan supplies provider orders,
quantities, dependencies, planned release times, and the UTC simulation start;
a separate versioned plan-execution scenario supplies the deterministic seed,
provider-profile references, and incident-generation mode. Resolve each
selected plan provider ID to exactly one profile source_provider_id and each
actionable product node's ETO reference to a configured provider capability;
reject missing or incompatible mappings. Run one lightweight SimPy actor per
provider order in a shared virtual clock. An actor may begin no earlier than
its planned release and only after every upstream provider order reaches
DELIVERED. Retain the existing lifecycle for purchase and work orders, treating
DELIVERED for a work order as transfer of its completed output to the next
production step.
Rationale: Plan-driven execution should be causal, deterministic, compatible
with the existing raw-message and reconciliation contracts, and inexpensive to
run locally.
Consequences: Existing scenario-driven simulation remains supported. New runs
record and fingerprint the source plan, emit one chronological linked truth and
message stream across all provider orders, and fail rather than invent a
provider or capability mapping. Work-order delivery is a simulation handoff
semantic, not physical freight. No OS thread, broker, database, distributed
worker, or real-time wait is introduced.

[D-034]
Date: 2026-10-11
Status: IMPLEMENTED
Decision: Remove material lead-time editing from the Product Designer. Product
authors configure product structure, quantities, units, ETO references, and
provider candidates, but no longer supply an operational material lead time.
Until provider-specific planning replaces Planner v1 scheduling, preserve an

separate planner contract change.

[D-035]
Date: 2026-10-11
Status: IMPLEMENTED
Decision: When deleting a Product Designer selection, enumerate every selected
Cytoscape node and remove its matching entry from the in-memory recipe before
removing the graph collection. Continue rebuilding all dependency requirements
from the remaining graph edges.
